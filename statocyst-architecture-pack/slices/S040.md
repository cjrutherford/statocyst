# S040 — Capacitor native-parity performance overhaul

**Milestone:** Polish / daily driver (follow-on)
**Status:** IMPLEMENTED_UNVERIFIED
**Depends on:** S038 (mobile UX polish — open items absorbed here), S029/S030 (downloads and cache)
**Reference device:** Google Pixel 10 Pro (physical). Emulator results are functional only, never
the acceptance gate.

## Objective

Make the Capacitor Android and iOS clients feel native: startup, scrolling, navigation,
playback feedback and the Now Playing screen should meet native frame-pacing and latency
budgets, while keeping the existing architecture (Angular shell in the WebView, Media3 /
AVPlayer service authoritative for audio).

This slice also fixes the phone Now Playing transport layout and adds per-track favorite and
download actions there.

## Baseline (main `76f4039`, version 1.9.0 / versionCode 27)

Measured with the production web bundle in headless Chromium at a 390 × 844 phone viewport,
with a mocked native bridge and one playing track. These are code/layout baselines, not device
performance numbers; phase 0 replaces them with physical-device measurements.

| Area | Observation |
| --- | --- |
| Now Playing controls | The `.controls` row is 350 CSS px wide, but its five buttons occupy only 20–308 px. The play button centre is x=164 while the content centre is x=195 (31 px left), leaving ~62 px unused on the right. |
| Volume | Volume trigger and slider sit in a separate `.volume` row below the transport, not inline with the other controls. |
| Current-track actions | The Now Playing screen has no favorite or download action, although `FavoritesStore` and `DownloadsStore` already exist. |
| Startup bridge | `LibraryStore.init()` requests `listTracks()` and `stats()` in parallel; `CapacitorBridge.stats()` calls `listTracks()` again, so the whole Room catalog is queried and serialized across the bridge twice on every cold start. |
| Settings startup | `CapacitorBridge.getSettings()` performs ~11 sequential `Preferences.get` round-trips before the shell can boot. |
| Position updates | The native plugin emits `playerPosition` every 500 ms; each event replaces the single playback snapshot signal read by the shell and views. |
| Library rendering | The track table creates a component tree and artwork element for every row. `content-visibility` helps paint, but 10k rows are still instantiated, diffed and held. |
| Continuous effects | `background-attachment: fixed` on three radial gradients, `backdrop-filter` on the fixed player bar/sidebar, animated `box-shadow`, animated `height` equalizers, blur filters, sonar/float loops and long entrance animations all run inside the WebView. |
| Android lifecycle | `MainActivity` force-resumes the WebView on `ON_PAUSE` and holds a partial wake lock even though playback is native. This keeps WebView rendering, timers and animations alive off-screen. |

## Scope

### In scope

- Startup latency and bridge payload reduction.
- Library list virtualization, including keyboard and row-action behaviour.
- A native-only rendering profile that renders the ocean/bubble identity (deep-water gradients,
  pearl highlights, sonar and bubble motion, light and dark themes) with cheaper paint paths,
  without changing the desktop presentation.
- Playback position/state subscription split so high-frequency updates do not re-render the shell.
- Android WebView lifecycle and progress-event throttling.
- Edge-to-edge phone layout on every device, including safe-area insets.
- Phone Now Playing: full-width transport, inline volume, favorite and download actions.
- Performance harness, budgets, before/after evidence and the release version bump.

### Out of scope

- Rewriting the UI in Jetpack Compose / SwiftUI.
- Changing the audio pipeline, queue authority, download policy or database schema.
- New runtime dependencies.
- Desktop visual redesign.
- iOS-specific WebKit tuning beyond the shared native profile (measured separately if a
  physical iOS device is available).

## Work plan

### Phase 0 — Baseline harness and budgets

1. Add `tools/android-perf.sh` (or extend `tools/android-device-matrix.sh`) to capture:
   - cold start (`adb shell am start -W`), warm start;
   - `dumpsys gfxinfo` jank/frame percentiles after a scripted scroll and Now Playing interaction;
   - `dumpsys meminfo` for the app process;
   - an optional Perfetto trace for a scroll + playback session.
2. Add renderer marks (`performance.mark`): `shell:interactive`, `library:first-paint`,
   `library:settled`, `now:interactive`. Expose them through a debug-only plugin call so the
   harness can read them from logcat.
3. Seed a 10k-track catalog with the existing fixture/seeder tooling; record the device model,
   Android/WebView version and refresh rate.
4. Write the baseline table into `evidence/S040-report.md` with status `IN_PROGRESS`.

**Gate:** one reproducible reference device/emulator profile, baseline numbers committed.

### Phase 1 — Startup and bridge payload

1. Remove the double catalog transfer:
   - `CapacitorBridge.stats()` must use the native `libraryStats` call or be computed from the
     single `listTracks` result; it must never trigger a second catalog read.
   - Add a native `librarySnapshot` method (additive) that returns `{tracks, stats}` from one
     Room query, and have the Capacitor bridge prefer it.
2. Make settings loading one round-trip: parallelize the `Preferences.get` calls (or add one
   native settings call) and cache the settings object in memory.
3. Stop blocking first paint:
   - Render the shell immediately; replace the full-screen boot overlay with in-place skeletons.
   - Run settings/playback/library/download initialization with `Promise.all` where independent.
   - Defer the non-active views (settings, playlists, offline, Jellyfin panel) with Angular
     `@defer` so their code and DOM are not created at startup.
4. Cache the last successful library snapshot (versioned IndexedDB/localStorage) so the first
   paint can show catalog rows while native data refreshes in the background.
5. Skip constructing the renderer `<audio>` element on native when the native playback bridge is
   active.

**Gate:** cold start and time-to-library within budget on the reference device; no duplicate
catalog query in a bridge trace.

### Phase 2 — Rendering and interaction

1. Virtualize the track list:
   - windowed rendering of a fixed-row table with overscan; keep real `<table>` semantics,
     sticky header, selection, long-press/context menu, keyboard focus and screen-reader labels;
   - chunk the album/artist grids so they do not build every card at once.
2. Split high-frequency playback state:
   - add a dedicated `positionMs` signal (and duration) to `PlaybackStore`;
   - keep the coarse `snapshot` signal for state/track/modes only;
   - let the seek bar/time labels subscribe to the position signal;
   - reduce the native ticker to 1 Hz and interpolate the visible position with
     `requestAnimationFrame`, or keep the 500 ms tick but avoid shell-wide invalidation.
3. Add a synchronous native rendering profile that preserves the ocean/bubble identity:
   - set `document.documentElement.dataset.native` in `main.ts` before bootstrap;
   - under `[data-native]`, replace live `backdrop-filter` glass with layered translucent
     gradients and a single pre-rendered bubble/pearl layer;
   - move the body gradients from `background-attachment: fixed` to one fixed, composited
     pseudo-element so scrolling does not repaint them;
   - keep sonar/bubble/float motion on transform and opacity, and replace animated
     `box-shadow`/`height` with opacity/transform pseudo-elements;
   - keep both light and dark theme tokens unchanged; keep the full glass presentation on
     Electron/desktop.
4. Add containment (`contain: layout paint style`) to list rows, cards and the player chrome;
   remove hover-only transforms on coarse pointers.
5. Keep artwork lazy/async and ensure off-screen virtual rows never request images.

**Gate:** 10k-track scroll and Now Playing interaction meet the frame budget; no long tasks
over 100 ms during scroll or search.

### Phase 3 — Native WebView and event throttling

1. Stop force-resuming/pausing the WebView in `MainActivity`; let `BridgeActivity` apply the
   lifecycle. The Media3 service remains authoritative, and the plugin re-emits state, queue and
   position on resume.
2. Remove the playback wake lock unless a measured playback case proves it is required; keep
   wake behaviour in the native service if needed.
3. Tune the WebView for a static app shell: hardware layer, no overscroll glow, offscreen
   pre-raster, correct background colour, no debug flag in release.
4. Coalesce `downloadProgress`, `downloadQueue`, `importProgress` and `cacheChanged` events to a
   capped rate (about 4 Hz) and do not emit when no listener is attached.

**Gate:** playback continues when the UI is backgrounded; notification/lock-screen controls
still work; resume restores position and queue; background CPU/battery check shows no
continuous WebView work.

### Phase 4 — Now Playing transport and actions

1. Transport layout:
   - phone: one full-width transport grid, all controls distributed edge-to-edge, play button
     exactly centred (7 equal cells: favorite | shuffle | previous | play | next | repeat |
     volume, or a symmetric equivalent);
   - desktop: keep the current row but move the volume trigger into it.
2. Volume: remove the separate `.volume` row; anchor the popover to the inline trigger and keep
   it on-screen at 360–430 px widths. Keep the playing/buffering state visible without adding a
   second control row.
3. Favorite: inject `FavoritesStore`, add a heart icon (outline/filled), `aria-pressed`, 44 × 44
   touch target, and toast-free optimistic toggle (toast only on failure).
4. Download: inject `DownloadsStore`, show only when `downloads.supported` and the track is not
   a local file. States: download, queued/downloading with progress, downloaded (tap to remove).
   Local tracks read "On this device" instead of offering a redundant download.
5. Add the needed icons (`heart`, `heart-filled`, download-done state) and accessible labels.
6. Update the mobile visual tests to assert:
   - the controls span the content width with no unused right gutter;
   - play centre equals the viewport centre within 2 px;
   - the volume trigger is inside the transport row;
   - favorite toggles and download calls reach the bridge with the current track id.

**Gate:** phone screenshots at 360, 390 and 430 px; desktop screenshot unchanged; all existing
e2e and unit tests pass.

## Acceptance gates

- Cold start to interactive shell: ≤ 1.5 s p50 on the Pixel 10 Pro, ≤ 2.5 s on a low-tier device.
- 10k-track library: ≥ 55 fps p95 scroll, no frame over 100 ms, search response ≤ 100 ms.
- Now Playing: transport fills the phone width; play centred ±2 px; volume inline; favorite and
  download work for the current track.
- Playback: audio never depends on WebView activity; position UI stays smooth; background
  playback and lock-screen controls unaffected.
- Desktop: no visual regression and the existing suite stays green.

## Risks and mitigations

- **Emulator results are not device results.** Use a physical mid-range Android device as the
  reference; keep the emulator for functional checks. If no device is available, mark the device
  gate `BLOCKED` with a reproduction recipe.
- **Virtualization can break a11y/row actions.** Keep real table rows and test keyboard focus,
  selection, long-press and context menu explicitly.
- **Native visual profile changes the look.** Gate it behind `[data-native]`; keep desktop
  pixel-compatible and capture screenshots.
- **Lifecycle change affects background playback.** The service is already authoritative; test
  background, lock screen, notification and Android Auto after the change.
- **Bridge API changes must stay additive** so desktop and older native builds keep working.
